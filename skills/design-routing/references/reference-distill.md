# Distill a supplied UI reference

Use this when the user wants a supplied image, URL or sample content turned into a reusable Markdown design brief, either as a reference-only deliverable or as input to a build. It is preparatory analysis, not a rendered direction or a completed gate. Write one project Markdown file from `../templates/reference-design.md`; keep the user's own links and constraints first. If the user also asks to build a new interface, continue the seven steps and the existing [direction gate](direction-gate.md).

1. **Record the source and question.** Name the supplied image/content or direct sample URL, the user goal, what surface was available, and the date and viewport if actually inspected. A gallery home page is only a lead. If a link cannot be opened, say so and work only from material already visible; do not invent a deep link, rendered state or access result.
2. **Separate observation from interpretation.** For each visible claim, note the exact part of the sample that supports it. Analyze content order, layout zones, hierarchy, density, alignment, visual motif and the user's task. Then label the design inference and a way to test it. A static image cannot establish actual font files, color tokens, DOM, keyboard behavior, motion timing, responsiveness or rights. Text-only material cannot establish layout. Mark those fields `unknown` until inspected on the right surface.
3. **Describe reusable decisions, not a clone.** State what to keep, change or reject for this product and why. Describe typography roles and color relationships without asserting an exact family or hex from a screenshot. For interactions, record only observed triggers and states; if motion is relevant, inspect a live sample and distinguish its behavior from a proposed hypothesis. Do not copy code, assets or screenshots into the design output. Check the exact item's rights before later use.
4. **Hand off a choice.** Give the user a concise reference summary and unresolved questions. Record the source or design constraints they prefer in the Markdown. This can feed Step 1–4; it does not pick a direction for them. An actual new visual design still needs the three rendered alternatives and Step 4 choice unless the user explicitly waives that gate.

Use the existing [prototype playbook](prototype-playbook.md) for flow/state questions, [typography](typography-en-vi.md) for EN/VI font checks, [color protocol](color-protocol.md) for deriving and testing colors, [image sourcing](image-sourcing.md) for asset provenance, and [motion playbook](motion-playbook.md) for animation decisions. These guides remain authoritative for their topics. A reference or vendor claim does not override the skill's quality floor.
